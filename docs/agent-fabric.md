# Agent Fabric

Agent Fabric is Omarchy Ultimate's durable, per-user control plane. The provisional foundation supplies a real owner-scoped daemon, a bounded versioned RPC transport, SQLite state, durable events, a code-owned typed-provider registry, fake transport providers, diagnostics, and one hermetic consequential reference operation with an append-only evidence ledger. The reference operation proves the Trust and lifecycle seams without mutating the host; the typed registry proves production provider admission and read dispatch but does not yet claim a general durable provider-operation coordinator, managed-agent runtime, production system executor, or final product UI.

## Authority boundary

`omarchy-fabricd` owns user-scoped Fabric transport and state. It listens only on `$XDG_RUNTIME_DIR/omarchy/fabric.sock`, creates its socket with mode `0600`, and requires Linux `SO_PEERCRED` to prove that every peer has the daemon owner's UID. A missing socket handle, unavailable credential facility, malformed credential record, or credential read failure is denied rather than treated as trusted. State lives at `${XDG_STATE_HOME:-~/.local/state}/omarchy/fabric/fabric.db`. The socket and state directories are mode `0700`; symbolic-link, wrong-owner, non-socket, and ambiguous stale-socket paths are refused.

Socket ownership identifies only the operating-system UID. It does not make a client a trusted UI, provider, agent, administrator, or undo authority. After `hello`, the daemon admits the generic owner RPC endpoint as one shell principal and binds a fresh session identity to that connection. Principal issuance succeeds before the connection is marked handshaken, so an authority failure leaves `hello` retryable rather than creating an authenticated connection without a principal. The session expires after eight hours, and every post-handshake RPC resolves the cached connection principal through daemon-owned active, revocation, and expiry state before dispatch. This fixed admission is sufficient to exercise exact operation approval for the fake reference provider, but it conveys no standing consequential grant and cannot authorize another provider, a task, or privileged work. Production endpoint admission, trusted consent UI, task-scoped proxies, secret handling, and sandbox boundaries remain separate Trust Plane obligations.

The daemon exposes no general process execution method. Its legacy transport-test registry accepts only declarative `fake.*` or `test.*` providers with in-process `echo`, `constant`, `counter`, `delay-echo`, and structured `error` behavior. The product-facing registry admits only provider objects selected by daemon code. It validates a closed `provider-manifest-v0` document, the exact declared Draft 2020-12 schema set, protocol compatibility, asynchronous hooks, risk/effect consistency, and immutable registration fingerprint before publishing the provider. No request field selects a provider implementation, executable, helper path, command line, schema, or shell string.

Typed provider reads are the only direct product-facing dispatch currently allowed. The registry schema-validates normalized arguments before calling the provider, applies an eight-second deadline, rejects a result from an obsolete provider generation, schema-validates the finite bounded result, and normalizes unstructured failures without leaking exception text. Provider disconnect and re-registration use compare-and-swap generations. An incompatible provider remains visible in the catalog with an update recovery action but cannot serve calls. The internal preflight seam may validate and freeze an operation plan for a future coordinator, but it returns no apply handle. An action declared as an operation is categorically rejected by the read path with `operation.durable-route-required`; leaf lifecycle hooks and a successful preflight alone never authorize mutation.

Provider implementations that eventually require a process must use a code-owned `FixedArgvCommand`: an absolute executable and immutable argument tuple established by provider code. Typed request values may enter through a validated stdin payload or another provider-owned channel, never by extending argv. `run_fixed_argv` always invokes the exact vector with `shell=False`; neither helper is reachable from provisional RPC.

## Transport contract

The socket carries one UTF-8 JSON object per newline. A frame may contain at most 65,536 bytes before its newline terminator. Invalid UTF-8, duplicate JSON object keys, non-finite numbers, non-object envelopes, and malformed JSON receive structured errors. Oversized and truncated frames are fatal to that connection; a malformed but bounded complete line does not poison the next line.

Every request contains exactly `protocol`, `id`, `method`, and `params`. `protocol` is `omarchy.fabric.rpc/v0`; `id` is a non-empty client-generated string no longer than 128 UTF-8 bytes and cannot be reused on the same connection. Responses echo the ID and contain exactly one `result` or structured `error`. Push events contain `protocol` and `event` but no request ID. The machine-readable envelope is `default/fabric/schema/rpc-v0.json`, which consumes the root-owned `common-v0.json` error and identity vocabulary.

The first request on each connection must be `hello`. The client declares an inclusive minimum and maximum integer protocol version; the daemon refuses ranges that do not overlap its supported range. The v0 methods are:

- `hello` — negotiate the protocol and create a connection identity.
- `version` — report protocol and readable database schema versions.
- `health` — report daemon, SQLite, socket, provider, and subscription health.
- `provider.register` — register an explicitly fake declarative provider, durably and idempotently when its definition is unchanged. Provisional v0 registrations are immutable; changing a registered version or definition is a conflict until a later provider-lifecycle contract defines safe replacement.
- `provider.list` — list registered fake providers and their named actions.
- `provider.invoke` — invoke a fake action with a required idempotency key and normalized JSON arguments.
- `provider.catalog` — list code-owned typed providers, their closed manifests, immutable fingerprints, protocol state, and lifecycle generations.
- `provider.read` — validate one typed read action and its result through the provider-owned schema pair. Operation actions fail closed and must enter a durable preflight/approval route.
- `reference.operation.preflight` — bind a lowercase UUID, idempotency key, hashed 32-byte recovery credential, endpoint principal/session, one fake resource revision, and the closed `desiredState`, `outcome`, and `pace` argument object.
- `reference.operation.approve` — issue a five-minute, one-use approval for the exact normalized operation after the caller explicitly confirms the reference-only consent contract.
- `reference.operation.start` — require the same endpoint principal and session, consume the exact approval through `PolicyEngine`, durably authorize the operation, and schedule its fake-provider lifecycle.
- `reference.operation.get` — inspect durable status, checkpoint, progress, error/result, and current fake resource state when called by the frozen endpoint session or with the exact recovery credential.
- `reference.operation.cancel` — durably request cancellation from the frozen endpoint session; a replacement session may use the exact recovery credential to cancel an interrupted operation or terminally abandon an awaiting-consent operation whose origin session was lost. Cancellation before start is immediately terminal, while cancellation after the applied checkpoint reconciles the fake resource to its preflight state.
- `reference.operation.reconcile` — require the frozen endpoint session or exact recovery credential, inspect an interrupted checkpoint after daemon restart, and either resume an unapplied operation or validate/reconcile an applied operation without guessing.
- `reference.operation.ledger` — verify and return the operation's bounded SHA-256 evidence chain to the frozen endpoint session or recovery-credential holder.
- `events.subscribe` — subscribe to up to 32 named topics or `*`, with bounded durable replay.
- `events.unsubscribe` — remove a connection-owned subscription.

Unknown fields and unknown methods fail closed. A client reconnects with a new hello handshake. Reusing a fake invocation idempotency key with the same provider version, action, and normalized arguments replays the durable outcome; using it with different arguments is a conflict. A daemon restart marks a pending fake invocation interrupted, and a later retry reports unknown change state and requires reconciliation instead of guessing or running it again. Typed provider manifests are defined in `default/fabric/schema/provider-manifest-v0.json`; their action contracts reference an exact provider-owned schema ID and version, and the registry refuses missing, extra, open, unresolved, or undeclared external contracts. Reference-operation parameter and result shapes are defined in `default/fabric/schema/reference-operation-v0.json`; every input object is closed and every enum, identifier, evidence count, and progress value is bounded.

## Consequential reference operation

`fake.reference-settings` is built into the daemon solely as a lifecycle contract exerciser. It never launches a process, writes outside the Fabric database, reads desktop or system state, or enters the declarative provider registry. Its only resource state is `enabled` or `disabled` in `reference_resources`, with a monotonically increasing `revision.N` token. The typed `outcome` is either `succeed` or `fail-after-apply`; the latter deterministically exercises failed validation and rollback. The typed `pace` is either `immediate` or a fixed observable delay for cancellation and crash tests, so callers cannot request arbitrary sleeps or unbounded work.

Preflight freezes provider version, resource identity, current revision, before state, normalized arguments, principal, session, recovery-token digest, and idempotency fingerprint. Principal and session fields are immutable after insertion: a second connection cannot replay preflight, approve, start, replay start, inspect, cancel, reconcile, or read evidence merely because it has the same Unix UID. The caller MUST generate a fresh 32-byte recovery token with a cryptographically secure random number generator, encode it as unpadded base64url, and retain it before sending preflight; the schema proves only its 43-character shape, not its entropy. Fabric stores only its SHA-256 digest and never includes the token in operation state, events, ledger evidence, or errors. The shell principal cannot hold a standing consequential grant, so `start` reaches the worker only after `ApprovalAuthority` binds the frozen fields and `PolicyEngine` consumes the one-use approval with `policy.approved`. Authority memory is explicitly bounded, expired and consumed records are pruned before issue, and an approval is discarded if its durable operation binding fails. The provisional `approve` RPC is deliberately confined to this host-inert fake operation; it demonstrates the authority-owned approval binding but is not a trusted production consent surface.

Execution persists `authorized`, `validated`, and `applied` checkpoints in the same SQLite transactions that record evidence and publish durable events. The fake resource update and `applied` checkpoint are atomic. Cancellation before apply finishes without a state change; cancellation after apply restores the preflight value and increments the resource revision so the rollback is observable. `fail-after-apply` follows the same reconciliation path and finishes with `reference.validation-failed` and `changeState: none`. Unexpected post-apply drift instead atomically records `interrupted`, the observed fake state, `changeState: unknown`, and `validation.recovery-required`; it never advertises reconciliation from a terminal state.

If the daemon stops after authorization but before a terminal result, startup changes the operation to `interrupted` and records `daemon.recovery-required`. Because restart creates a new endpoint session, that session must present the exact operation recovery token to inspect, cancel, or reconcile the interrupted record. An awaiting-consent operation is not started or rebound after its in-memory approval authority disappears; its token may only terminally cancel it. The token cannot authorize approval, start, start replay, or cancellation of queued or running work. Reconciliation never reruns an unknown apply. An unapplied checkpoint may be queued again, while an applied checkpoint must exactly match the desired fake state and expected revision before it can finish as `recovered`; cancellation and deterministic failure instead roll back from that exact checkpoint. Applied reconciliation validates and finishes directly from `interrupted` in one SQLite transaction, so a mismatch leaves the operation interrupted and safely retriable rather than stranded in an intermediate state.

Every ordinary state transition appends an evidence row containing an entry UUID, operation UUID, event type, typed payload, prior hash, entry hash, and timestamp. The hash covers the complete entry and the prior hash, producing one per-operation chain rooted at 64 zeroes. The operation row atomically anchors the expected entry count and head hash, so ledger reads reject tail deletion and an emptied chain as well as altered payload, ordering, predecessor, or hash. Every append verifies the complete existing bounded chain in the same transaction before changing operation or resource state, so middle-row corruption cannot acquire a valid new tail. Reads use the same verifier but return at most eight entries per page through `afterSequence` and `limit`, keeping every RPC response far below the 64 KiB frame ceiling. An operation is capped at 128 evidence entries and four approval issues. If a malformed, corrupt, or full evidence chain prevents another append, Fabric rolls back the attempted transition and terminally fails only that operation with an explicit evidence error and no fabricated ledger entry; daemon startup and unrelated operations continue.

## Durable state and events

SQLite operates in WAL mode with `synchronous=FULL`, foreign keys enabled, and an owner-only database file. `PRAGMA user_version` and `schema_metadata` record the database contract. The daemon declares explicit minimum and maximum readable schema versions and refuses newer, too-old, unversioned non-empty, or corrupt databases without attempting a guessed repair.

Each schema migration runs in its own `BEGIN IMMEDIATE` transaction. Before migrating an existing supported database, Fabric creates an owner-only SQLite backup beside the database with a `pre-migrate` suffix. A failed migration rolls back its schema and version together.

Events receive a UUID, monotonic SQLite sequence, stable topic, finite-JSON payload, and creation time. Publication is durable before live fan-out. The default history retains 512 events; each subscription may replay at most 128 events, and each connection may own at most 32 live subscriptions. Replay envelopes are size-checked before the live subscription is installed, so an oversized reply cannot leak a server-side subscription. A cursor older than pruned history fails with `events.cursor-expired`, and a replay larger than the declared limit fails with `events.replay-limit`. Server and client live-event queues are both bounded. Server overflow produces an explicit `fabric.subscription-overflow` event and ends that subscription; client overflow closes the connection with `events.client-overflow`. Both paths require reconnect and durable replay rather than silently losing state or growing memory without bound.

## Diagnostics

The provisional commands remain hidden from normal Omarchy command listings until packaging and product routing are integrated:

```bash
omarchy-fabricctl health
omarchy-fabricctl doctor
omarchy-fabricctl --json health
```

`health` checks the live daemon through the same hello and RPC path as every other client. `doctor` additionally evaluates database integrity, WAL mode, and owner-only socket permissions. If the daemon is unavailable, diagnostics fail honestly and recommend restart or reconnect; they do not inspect a stale database and call it healthy.
