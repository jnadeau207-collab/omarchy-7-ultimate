# Administration, update, recovery, backup, and diagnostics providers

This tranche adds twelve typed Fabric provider leaves for system administration and recovery planning. The leaves extend the existing central `LeafProvider`, provider registry, closed JSON Schema contracts, stable state revisions, and read-only probe boundary. They do not add a second daemon, provider registry, operation coordinator, privilege helper, discovery mechanism, or mutation route.

## Safety boundary

Every real provider is inventory-only. It runs only code-owned `FixedArgvCommand` values with an absolute executable and immutable arguments, never appends request data, never invokes a shell, and never calls `sudo` or `pkexec`. The shared `ReadOnlyProbeBackend` reports `operation=false` with a structured reason even when inventory succeeds. Missing dependencies, failed probes, timeouts, malformed output, duplicate identities, and oversized inventories remain explicit unavailable or invalid states.

Operation actions are typed plans exercised through hermetic fake adapters. Their apply hooks mutate only fake provider state so the central preflight/apply/validate/rollback seam can be tested. They do not terminate a process, authorize hardware, mount or format storage, alter CUPS, edit accounts, change firewall rules, control systemd units or timers, install packages, reboot, restore a snapshot, access a backup repository, create an archive, or upload diagnostics.

## Durable update lifecycle

`UpdateJournal` persists one finite canonical JSON document through mode `0600` create-and-replace writes with an fsync before rename and a directory fsync after rename. Its directory must already exist, be owned by the caller, be non-writable by other users, and contain no symbolic-link traversal; the journal and lock must be private caller-owned regular files opened with `O_NOFOLLOW`. A bounded `flock` serializes separate threads, objects, and processes. Every document carries a content revision, so concurrent or restarted callers cannot advance stale intent. Cancellation is valid only for proposed, checking, downloading, or staged work; applying and later states require reconciliation. Apply cannot cross into package application until checkpoint creation is observed. An interrupted run derives waiting-reboot, succeeded, failed, or needs-attention exclusively from closed observed package, checkpoint, catalog, and reboot truth; catalog drift or a missing or failed apply checkpoint requires attention rather than success.

Duplicate JSON keys, non-finite values, mode-inconsistent status or checkpoint combinations, malformed digests, tampered revisions, oversized journals, unsafe paths, and non-private files fail closed. Sensitive-looking transition detail is replaced before persistence. The journal does not execute the update; it is the provider-owned lifecycle model for later central operation-coordinator integration.

## Restore and backup scope

System restore and home backup are intentionally different domains. A recovery resource can only declare `scope=system`, and fake construction rejects any mixed or home-scoped restore inventory. Snapper's current row is not emitted as a restore point, snapshot numbers and timezone-bearing creation times are canonicalized, arbitrary snapshot descriptions contribute only to the private revision digest and are withheld from output, and list output alone never fabricates eligibility, health, or read-only truth. A recovery plan requires independently verified `eligible=true`, `health=healthy`, and `readOnly=true`, fixes `preservesHome=true`, and does not accept a target path.

A backup resource can only declare `scope=home` and `engine=restic`. Real inventory requires every Restic snapshot to report one or more canonical paths under the configured `/home/<user>` root; absent paths, mixed scopes, duplicate paths, uppercase or duplicate IDs, and timestamps without timezone truth fail closed. The newest 64 snapshot IDs are selectable and explicit truncation truth is published. Restore accepts one of those exact IDs plus a bounded relative path whose components reject traversal, absolute paths, backslashes, NUL, shell metacharacters, and excessive depth. The default retention contract keeps seven daily, four weekly, and six monthly snapshots. The threat model explicitly covers accidental deletion, disk failure, malware, and repository loss; a single repository is not represented as protection from repository loss.

## Diagnostic privacy

Diagnostics return three structured checks: failed services, journal disk use, and filesystem capacity. Failure of one probe becomes an unavailable check rather than fabricated success or loss of the other checks. Probe stderr and arbitrary exception text are not copied into the result.

Support bundle output is a preview only. Callers choose from the three provider-owned source IDs and a maximum byte count from 1 KiB through 1 MiB. Each fixed probe is capped at 256 KiB, and unavailable sources cannot enter a plan. Only normalized titles, statuses, counts, and evidence enter preview state; raw `systemctl`, `journalctl`, and `df` output is never retained there. Redaction runs before byte accounting and excerpt generation with linear-time bounded patterns. No archive is created, no arbitrary path is read, and no upload exists in this tranche.

## Contracts and defaults

The public projection schemas are `admin-inventory-v0.json`, `update-plan-v0.json`, `recovery-point-v0.json`, `backup-plan-v0.json`, and `diagnostics-bundle-v0.json`. Every object is closed, every document declares Draft 2020-12 and `x-omarchy-version=v0`, and every revision uses the canonical SHA-256 vocabulary.

`default/ultimate/administration/provider-catalog-v0.json` publishes all twelve administration, update, recovery, backup, and diagnostics leaves in explicit provider-ID order and pins `executionBoundary=plan-only` plus `authorizationBoundary=central-fabric`. `default/ultimate/recovery/policy-v0.json` pins checkpoint, cross-process journal locking, private journal files, verified restore truth, verified backup paths, bounded selectable snapshots, structured diagnostic evidence, retention, threat, redaction, and no-upload defaults. These files are declarative product contracts; production registration remains a static code-owned list and never scans them for factories.

## Integration seams and limitations

The central builtin provider list imports each of the twelve builders by a hard-coded code-owned name. Construction isolates each builder and admission independently, and the backup builder receives the authenticated daemon account's canonical home from `getuid` plus the OS account database rather than `HOME`, RPC data, or an environment-selected factory. Filesystem discovery, import strings from requests, dynamic manifests, and generic root helpers remain forbidden. Operation plans still require the durable authorization and operation coordinator.

Real mutation remains unavailable until each operation receives a dedicated least-privilege executor, durable approval semantics, exact postcondition validation, interruption recovery, and metal acceptance coverage. Direct leaf preflight is not an authorization boundary: production routing must remain behind the central Fabric principal, capability, approval, and operation coordinator named by the catalog. SMART is intentionally not guessed from `lsblk`; service and timer enablement are `unknown` when their chosen inventory command does not prove enablement; device authorization, printer acceptance, account lock, and administrator-group state remain unknown until dedicated trusted probes are added. Restic availability still depends on a configured repository and credentials supplied outside RPC arguments, and the code-owned `home_root` integration parameter must come from trusted daemon configuration rather than RPC data. Snapper inventory proves only what the installed tool reports and never claims eligibility or restoration safety without a separate verifier.

The central leaf contract bounds every inventory at 64 resources. Process selection deterministically reserves capacity for user and system processes; device selection covers an explicit subsystem allowlist and prioritizes removable hardware; service selection prioritizes failed and active units. Every selected resource publishes the total observed count and whether the projection was truncated, so the bound is visible rather than silently presenting a partial inventory as complete.

Focused tests live under `test/fabric/administration`, `test/fabric/recovery`, and `test/shell.d/fabric-administration-recovery-test.sh`. They cover central registry admission, fixed argv, honest availability, complete fake lifecycle, state drift, restart persistence, duplicate identities, corruption, concurrent revisions, PID reuse, destructive confirmation, injection, cancellation, reconciliation, scope escape, and redaction.
