# Ultimate Capability Engines and Product Ownership Convergence — 2026-08-27

This is a later product-ownership tranche under the eleven phases in `plans/project-ultimate.md`. It is not W0, not founding authority, and not a replacement for that taxonomy. It joins the provisional Fabric foundations, durable managed-work store, typed domain families, standalone product applications, shell surfaces, package repository, ISO repository, and physical machine into one continuous convergence program after Phase 1 is closed. It is deliberately not a sequence of tiny named slices. The fleet rolls from one dependency-cleared ownership area into the next until the entire exit state below is satisfied.

## Outcome

The tranche ends with a dependency-complete capability engine and honest product ownership baseline:

- every reviewed production provider is explicitly registered in code, appears in health and catalog output, validates through the real socket, and has a visible product route;
- read-only state for presentation, connectivity, files/defaults, software, compatibility, administration, update, recovery, backup, and diagnostics is available through bounded typed contracts;
- every consequential action enters one durable operation coordinator with idempotency, approval, cancellation, checkpoints, postcondition validation, rollback/reconciliation, and append-only evidence;
- no client label, QML IPC target, provider name, manifest, filesystem scan, environment variable, or RPC actor field creates authority;
- durable tasks and Agent Center projections survive daemon and UI restarts under a stable account owner while endpoint sessions remain revocable and separately observable;
- Settings and Agent Center render real provider and managed-work results for every registered route, with explicit loading, empty, unavailable, denied, failed, stale, interrupted, recovery, restart, and reboot states;
- Files, Software Center, Compatibility Center, Administration, Recovery, Backup, and Troubleshooting have normal application ownership and consume the same providers as agents;
- the main repository, `omarchy-pkgs`, `omarchy-iso`, GitHub branches, and the physical machine end on one recorded release candidate with no hidden local diff or unaccounted worktree;
- Chrome right-edge geometry remains exact through floating, left/right snap, custom maximize, native maximize/restore, repeated cycles, and absolute pointer activation.

## Locked baselines

The following are invariants, not negotiable implementation suggestions:

- The verified Chromium compensation path and caption geometry are frozen. Any change that can affect frame extents, snap rectangles, maximize rectangles, borders, gaps, work areas, scale, or caption hit targets requires the complete real-Chrome metal proof before it can land.
- The normal per-user Fabric daemon never becomes root. Privileged work crosses a typed least-privilege executor or Polkit boundary with fixed code-owned commands and typed non-secret input.
- Product process identity is not authority. The current `fabric.owner-rpc` admission is recorded as shared; future product-role binding remains non-authoritative unless the daemon can establish it without trusting the caller label or argv.
- Provider registration is an explicit tuple of code-owned factories. Production never imports providers by RPC name, scans directories, loads entry points, or treats manifests as executable discovery.
- Consumer QML never owns a command, shell string, package transaction, filesystem mutation, privilege prompt, or direct fallback path. A missing provider produces a visible unavailable state.
- A preflight plan cannot be replayed after its observed revision, resource identity, executor version, policy revision, or prerequisite checkpoint becomes stale.
- Rollback and recovery never overwrite newer intent. Resource ownership, revision comparison, and reconciliation evidence are mandatory before compensating action.
- Root snapshots are system restore points, not home backups. Home backup scope, repository identity, snapshot inventory, and restore paths must be independently proven.
- Seeds, recipes, signatures, hashes, publishers, review states, and compatibility verdicts never claim verification without release-owned evidence.
- Secrets do not enter argv, logs, durable context snapshots, diagnostic bundles, operation evidence, notification history, search indexes, task records, or URLs.
- Every list, tree, event stream, log, artifact, query, and diagnostic source has byte, item, depth, and retention bounds with explicit truncation truth.

The entry baseline includes the provisional Fabric RPC/database/daemon, endpoint sessions, event broker, typed provider registry, reference operation lifecycle, system domain providers, capability graph, product contracts, standalone Settings and Agent Center hosts, and durable managed-work plane. The Chrome edge defect has physical-machine proof across every caption state and repeated geometry cycles. The main, package, and ISO repositories have been reconciled locally and on the physical machine.

## Continuous fleet ownership

Root owns shared seams for the entire tranche: daemon dispatch, database schema/version, session admission, `provider_builtins`, capability graph, product route registry, system executor protocol, operation coordinator, packaging pins, cross-repository commits, GitHub push, metal deployment, and final reconciliation. Agents do not independently edit these seams.

The rolling fleet uses three disjoint implementation owners at a time. When one owner completes, its slot immediately becomes an independent reviewer or the next dependency-cleared product family. A creator never performs the only review of its own tranche.

### Provider registry and catalog convergence owner

This owner integrates the reviewed provider builders only after root assigns the shared seam. The scope covers deterministic factory order, startup admission, provider health, unavailable/degraded truth, schema IDs, action modes, catalog output, real-socket read/preflight tests, exact provider counts, and failure isolation. It also maps Settings Apps to `defaults.provider`, Update to `update.provider`, Recovery to `recovery.provider`, and every standalone product route to one explicit provider or managed query.

The owner must prove that one broken or unavailable provider cannot stop daemon startup, corrupt another provider generation, leak stale catalog state, or make health claim availability. Duplicate IDs, schema conflicts, version incompatibility, oversized results, invalid manifests, callback timeouts, and re-registration races fail closed.

### Stable owner, context, managed work, and Agent Center backend owner

This owner integrates the durable managed-work plane without granting execution authority. Durable account ownership must survive endpoint reconnect while every request still records the active endpoint session. The first public surface is bounded read/query plus daemon-owned projections from reference operations, approvals, provider health, permission decisions, usage, and artifacts. Task/run/automation creation remains unavailable until actor admission, grants, scheduler ownership, and sandbox execution have their own reviewed authority.

The owner must prove restart, migration, corruption refusal, disk-full behavior, concurrent readers/writers, cursor isolation, retention, redaction, session expiry, cross-owner denial, projection revision monotonicity, and no secret persistence. Agent Center receives all twelve versioned query views through one constrained method family and never infers placeholder records.

### Durable operation and least-privilege executor owner

This owner generalizes the reference operation lifecycle into the only provider mutation path. A provider contributes schemas, current-state reads, preflight, fixed executor intent, postcondition validation, and compensation/reconciliation logic; it does not spawn an arbitrary command. The coordinator binds the operation to account owner, active endpoint, capability, resource identity, observed revision, provider generation, policy revision, idempotency key, approval, checkpoint, and executor contract.

The owner must cover cancellation at every boundary, connection loss, daemon restart, executor crash, system restart, reboot-pending state, stale plans, newer intent, partial apply, failed validation, failed rollback, recovery-token replay, event backpressure, ledger truncation attempts, and disk exhaustion. Representative low-risk user mutations from every provider family must pass through the coordinator before high-risk or privileged executors are enabled.

### Settings and Quick Settings product owner

This owner turns the standalone Settings host from a generic payload viewer into a complete route-driven product while reusing the existing compact Display, Audio, Network, Bluetooth, Input, and Power state models. It owns navigation, search, deep links, typed resource selection, staged changes, preflight summaries, approval/restart/reboot states, operation progress, cancellation, validation, rollback/recovery, unavailable providers, and responsive layout. Quick Settings consumes the same read models and action intents; it never becomes a second backend.

The product must cover Display, Sound, Network, Bluetooth and devices, Input, Personalization, Apps/defaults/startup, Power, Accessibility, Update, Recovery, and System Information. Missing engines remain visibly unavailable with a reason. Every page is pointer-complete, keyboard-complete, named for accessibility, long-string safe, high-contrast safe, reduced-motion safe, and verified at relevant scale/density combinations.

### Agent Center product owner

This owner consumes the managed-work query family and operation projections to build Overview, Tasks/Runs, Pending Approvals, Automations, Activity, History/Recovery, Context, Permissions/Trust, Usage, Providers/Accounts, Artifacts, and Troubleshooting. Every page has real empty/offline/stale/error/retry states, stable entity deep links, bounded pagination, explicit provenance, and no direct execution authority.

Agent Center may request an approved managed action only after the coordinator, task principal, grant, context snapshot, budget, sandbox, and cancellation contracts exist. Until then, controls are absent or honestly unavailable; they never simulate success.

### Files, Software, Compatibility, Administration, and Recovery product owner

This rolling ownership area builds normal taskbar applications for the reviewed domain engines. Files owns This PC, locations, disks, removable media, network locations, recent, Trash, archive, properties, conflict resolution, and scoped operations. Software owns catalog/installed/adopted state, provenance, preflight consequences, transaction progress, data disposition, restart, recovery, and source-specific trust. Compatibility owns inspection, route decisions, recipe evidence, isolation truth, host constraints, deployment/export/removal, and explicit unsupported outcomes. Administration owns Task Manager, Devices and Printers, Storage, Accounts, Firewall and Sharing, Services and Schedules, Update, Restore, Backup, and Troubleshooting.

These applications share the same provider and operation records used by agents. They do not create private models, hidden command paths, or optimistic completion state.

### Search, identity, shell convergence, and notification owner

This owner replaces heuristic cross-surface joins with the checked application registry and normalized search contract. Exact desktop IDs, compositor IDs, launch records, notification identities, installed records, pins, running groups, badges, progress, jump lists, recent items, provider routes, operation entities, and task entities join through stable IDs and explicit aliases only. Ambiguity is quarantined rather than guessed.

Start, Run, Settings, Files, Software, Compatibility, Agent Center, and the system menu emit or consume one normalized result shape with provenance, trust, rank, route, and typed action. Persisted raw notification commands remain non-agent-callable and are removed before release. Badges/progress/attention and operation notifications project from durable state rather than private timers.

### Package, ISO, migration, and release owner

This owner runs only after code and product routes have passed their dependency gates. It pins the main repository release in `omarchy-pkgs`, verifies file ownership and runtime dependencies, produces matching package versions, and records package contents. It then pins the package snapshot in `omarchy-iso`, verifies offline/fresh/upgrade behavior, and records the three-repository BOM.

Existing-user migrations are stock-state-sensitive, resumable, and reversible for one release. They do not overwrite customized defaults, XDG choices, themes, shell layouts, app associations, or user data. Service activation and database migration are idempotent. Rollback must restore the previous package/runtime pair and preserve durable user state.

## Execution order

The tranche is a dependency graph, not a collection of serial tickets:

1. Complete independent red-team repair of every provider family and land each family as an atomic commit with focused metal proof.
2. Register all reviewed read/preflight providers through the explicit production factory tuple and prove daemon startup, catalog, health, socket reads, failure isolation, and honest unavailable state.
3. Bind stable account ownership and read-only managed projections; expose all Agent Center queries without enabling managed execution.
4. Build the durable operation coordinator and unprivileged executor harness while Settings and Agent Center product owners build against the frozen read/query contracts.
5. Enable representative user-scope operations family by family only after stale-plan, newer-intent, restart, cancel, validation, rollback, and reconciliation proofs pass.
6. Build Files, Software, Compatibility, Administration, Recovery, Backup, and Troubleshooting applications in parallel with search/identity/shell convergence.
7. Enable reviewed privileged executors one narrow capability family at a time behind the common coordinator and exact Polkit contract; no consumer UI changes authority.
8. Run cross-surface mouse/keyboard/accessibility/fault campaigns, remove remaining direct-command debt, and activate migrations only when provider-backed paths are complete.
9. Pin packages, then ISO inputs, then run fresh/offline/upgrade/rollback certification and physical-machine proof.
10. Reconcile every local and metal worktree, GitHub branch, stash, generated artifact, transient service, temporary test checkout, and proof window into the recorded release candidate.

## Commit and deployment discipline

Each provider family, shared coordinator change, product application, migration, package pin, and ISO pin lands as a coherent atomic commit. A commit includes its contract, implementation, tests, and documentation. Shared-seam changes never hide inside a leaf-provider commit. Generated bytecode, transfer archives, screenshots, transient state, and local environment dependencies never enter Git.

Every good main-repository commit is pushed to `origin/work` and fast-forwarded onto the clean physical checkout. Package and ISO commits are pushed only after their own focused tests and cross-repository assertions pass. The physical checkout never carries an uncommitted patch as an implicit deployment.

- package file ownership, dependency, matching-version, migration, rollback, and ISO consumption assertions;
- no ignored bytecode, test databases, transfer archives, or generated caches under repository paths.

## Visual, accessibility, and physical gates

Every changed visible surface is restarted and inspected by the agent on the physical machine. Proof covers relevant window sizes, scale, density, keyboard focus, pointer action, screen-reader semantics, large text, long strings, high contrast, reduced motion, empty/offline/error/progress/recovery states, reopen placement, snap, maximize, task switching, and multi-monitor ownership. The user is never asked to substitute for this verification.

Chrome receives its locked regression matrix after any shell, compositor, theme, token, application-host, panel, work-area, or packaging change that might affect geometry. Passing automated geometry arithmetic without the real Chrome window and absolute pointer controls is insufficient.

## Tranche exit

This convergence tranche is complete only when the reviewed capability engines are production-registered, representative real operations use the durable coordinator, Settings and Agent Center own their full backend states, the major domain applications consume the same paths, search and identity join across surfaces, all three repositories are pinned and pushed, the physical machine is clean and exact, and the full automated/visual/security campaign has no unresolved data-loss, privilege, clipping, phantom-success, stale-progress, or recovery-scope defect.

Anything short of that remains an in-progress program state and must not be described as product-complete.
